The page you trade on is stored in eleven contracts.

zSwap's HTML lives on Ethereum mainnet as contract code. Eleven contracts hold the bytes; a twelfth reads them back and answers with the page. There is no server in the path and no file to pin, and the bytes at a given address can never be edited, including by us.

How the page reaches you

Storing a web page as bytecode

Anyone can read a deployed contract's code with EXTCODECOPY. zSwap treats that as a filesystem. The minified page is cut into slices; each slice is deployed with a small init stub that returns the slice as the contract's own runtime code. The wrapper then holds one immutable pointer per slice, DATA1 through DATA11.

01Slice the page. EIP-170 caps deployed code at 24,576 bytes, so the split is what keeps that ceiling off the dapp as a whole. Eleven is simply what 255,337 bytes needs: ten chunks would have to carry 25,534 bytes each.
02Deploy the chunks. Each one holds page bytes and nothing else.
03Deploy the wrapper with those addresses. Its constructor reverts unless every chunk is present, non-empty and distinct, so a missing or duplicated slice cannot be baked in by accident.
04Read it back. html() copies all eleven chunks into one ABI-encoded string, which any RPC client decodes without help.

Code is cheaper to deploy than the equivalent storage, and reads come back in a single copy. Storing the same HTML in SSTORE slots would cost roughly 20k gas per 32-byte word to write and a pile of SLOADs to serve. The pointers being immutable is what lets the dapp answer with Cache-Control: public, max-age=31536000, immutable and mean it: no function on the wrapper can change the bytes.

Reading it yourself

cast call <zswap-address> "html()(string)" --rpc-url <rpc> > zSwap.html
# open the file in any browser
What an upgrade actually does. Since html() can't be changed, fixing the page means deploying new chunks and a new wrapper, which the DAO does through deployNext. Every old version keeps serving its own bytes at its own address forever. Only the ENS name follows the new tip, and it waits out a three-day maturity period first. Bookmark an address and you stay on that build permanently.

Standards

ERC-8244 and the browsing path

Getting from a contract address to a browser tab takes four standards. zSwap answers all of them, so it works on whichever gateway or wallet a reader happens to have.

ERC-8244A contract with an html() function is a web page. The gateway calls html(), receives a string, serves it as text/html, and that is the entire standard. A gateway needs to know nothing about zSwap in particular, and the dapp implements nothing beyond the function it already had.
ERC-5219A fuller request interface. request(resource, params) answers with a status code, a body and headers; zSwap returns 200, the page, and its Content-Type and Cache-Control headers. Paths and query strings are ignored. It is one page, served from any URL under its address.
ERC-4804The web3:// scheme itself. resolveMode() returns "5219", which tells a client to use the interface above instead of guessing at calldata.
ERC-6821Name to contract. A gateway reads the contentcontract text record and falls back to the address record; zSwapResolver answers both, so either path arrives at the same version.

Three ways to open it

  • An ERC-8244 gateway: https://<address>.w4eth.io/
  • An ERC-4804 gateway: https://<address>.1.w3link.io/
  • A wallet or browser extension that speaks web3:// natively
  • By name, through the .wei gateway at zswap.wei.limo, which follows the resolver to whichever build is current and mature

zSwapResolver stores no address

The name is a .wei name in WNS, our own registry at 0x0000000000696760E15f265e828DB644A0c242EB. A .wei name is an NFT, and WNS resolves it to an address: id, then resolve. Pointing that name at this contract is what makes a gateway serve the current build. The resolver speaks the ENS resolver interface as well — addr(bytes32), ENSIP-9 coin type 60, and text for ERC-6821's contentcontract — so gateways written for either system land in the same place. The node argument is ignored, since the resolver is set on one name and answers for that name.

Usually a name has to be re-pointed after every upgrade, and that second transaction is the one people forget. Then the chain says v0.3 while the name still serves v0.1.

This resolver keeps no address at all. It walks the on-chain successor chain when it's read and returns the newest version that has cleared its maturity window, so the DAO's deployNext call is the name update too, in the same transaction. Contenthash is deliberately left empty: it names a blob, and there is no blob here. The DAO's only privileged power over the resolver is manage, a gated call into WNS and nowhere else, which exists so the name can still be renewed, re-pointed or handed back.

Execution

zRouter

zRouter is what the page transacts against. It speaks Uniswap V2, V3 and V4, Sushi, Curve, Lido and zAMM through a compact ABI, and reaches anything else through snwap: the input tokens go to a venue-specific executor, the executor is called, and the router measures the recipient's balance before and after. The output minimum is enforced on that measured difference, so a venue that misreports its own fill still can't underpay you.

The arbitrary call runs through SafeExecutor, a separate contract that holds no token approvals. It exists so that calling an unknown venue can never be turned into a call on the router's own allowances.

Multicall entries are delegatecalled, which is why a route that's part AMM and part resting order can settle as one transaction on one signature. ETH and WETH are interchangeable at the interface: the router wraps or unwraps whichever way the pool needs, in the same call. Deadlines revert as Expired, mismatched value as InvalidMsgVal, and a short fill as SnwapSlippage, which names the token, what arrived, and what was required.

Forwarders

Venues whose call shape doesn't fit snwap get a small adapter rather than a special case inside the router.

OrderbolPlacing orders. Routes into Swapboard, Dutchboard and Floorboard. A single-use checkpoint(token) in transient storage means an order can only ever be funded by the balance increase that arrived after the checkpoint, so tokens sitting at the adapter can't be swept into somebody's new order.
SwapbolFilling orders. Ask fills and bid hits, using exact call-scoped allowances that are revoked before it returns. Both sides live in one adapter because a route that's part ask, part bid and part AMM only works inside a single executor call.
SwapbatchBatched fills against the legacy Swapboard v1, which has neither a batch fill nor a multicall of its own.
CowolCoW Protocol, signing as a contract via ERC-1271.
FwabolFWA in both directions, unlocking the V4 PoolManager directly. FWA reverts transfers that don't touch the PoolManager, so an adapter that ever received it would be stuck holding it. This one never does: on a buy the PoolManager pays the recipient, on a sell the seller pays the PoolManager.

Pricing

zQuoter

Before anything is signed, zQuoter prices the trade across Uniswap V2, V3 and V4, Sushi, Curve, Lido, zAMM and the Precision pools, and the best route wins. AMM and orderbook reads are pinned to one block, so what you're comparing is a single moment rather than a spread of them.

V4 needs its own machinery, because a V4 pool can't always be priced by local math.

zQuoterV4Ordinary V4 pools. Stays a pure view by reading through StateView, and matches Uniswap's canonical quoter exactly.
V4QuoteLensPools with a hook. A hook can replace the curve, take a cut of the output, or set the fee per swap, and none of that shows up in slot0. This one runs the hook for real through PoolManager.unlock. That writes transient storage, so it isn't view, but eth_call simulates it fine.
V4PortExecutes any V4 pool in either direction.
Why V4 is quoted separately. The widely used base quoter computes a V4 swap fee as protocolFee + lpFee. But protocolFee in V4 isn't a rate: it's a packed uint24 carrying two 12-bit values. That sum was only correct while Uniswap left protocol fees at zero, and they were switched on at block 25,623,201. Measured live since then, the base quoter under-quotes the deepest ETH/USDC pool by about half and over-quotes others by three orders of magnitude. zSwap sends its V4 leg to zQuoterV4, where the fee rule is fixed.

What you see before signing

  • Slippage is the worst price you'll accept. Past it, the trade reverts instead of filling badly.
  • Price impact is how far your own size moves the price. The page warns as it grows and won't quietly let a terrible one through.
  • Min received or Max paid, the venue that won, and the effective rate.
  • Order discovery and route planning both run under bounds. When either one hits its limit, the page prints Book scan capped or Planner heuristic/capped, so you know a better combination may exist beyond what was searched.

Resting liquidity

Orderbooks

Three boards hold real escrow on-chain, and every quote consults them. When board liquidity beats the AMM price on part of a trade, the page builds a split route across both and takes it if the expected improvement clears a gas-aware threshold.

SwapboardA price you name. The order rests, fully escrowed, until someone fills it or you cancel. Partial fills are supported, and a WETH order can be cancelled back to native ETH.
DutchboardA price that falls. It starts above your floor and decays to it across a window you set. There are two clocks: the decay, then how long the lot rests at the floor before escrow returns to you. Set the second to forever and it waits until you cancel. Handles ERC-20 lots and NFTs.
FloorboardThe bid side. A standing offer that climbs toward a ceiling. The escrow is the payment, sized at the end price, because that's the most the bid can ever owe.
View lensesRead-only planners over the boards. SwapboardView caps planning at 256 candidates, drops all-or-nothing rows too large for the current request before spending that cap, and bounds token metadata calls by gas and returndata size. A hostile symbol() comes back blank rather than breaking the read.

Every position is an NFT that draws itself

An order on any board is an ERC-721, and its tokenURI is a self-contained SVG card rendered on-chain by an immutable contract the board deployed in its own constructor. Nothing is fetched at display time, so the card can't rot or go stale independently of the order it describes.

Listing an NFT without handing over your collection

Dutchboard will take an NFT by plain safeTransferFrom, with the sale terms ABI-encoded in the transfer's data. The conventional route needs a per-token approve, or in practice a blanket setApprovalForAll that leaves the board holding authority over every token you own in that collection long after the listing ends. Pushing the token grants nothing and moves exactly one item. Bundles still go through listNFT, since one transfer carries one token.

Sending, and SLOW sends

The page also sends plain transfers, resolving 0x, .eth, .wei and .gwei recipients. A SLOW send is time-locked and reversible by you at any point before it matures, which is worth using for large amounts and for addresses you haven't paid before. A locked transfer doesn't deliver itself; tick auto-claim and the page attaches a small keeper tip, refundable if you reverse the transfer.

Liquidity

Precision pools

A general-purpose AMM pays for its generality on every single swap: token addresses and fee tiers come out of storage, decimals are normalized at runtime, pool keys get hashed, hooks get dispatched. A Precision pool knows its pair, decimals, fee and curve parameters at compile time, so all of that becomes constants and the swap collapses to the curve math plus the transfer.

StableCurve's stableswap invariant at A=2000, written for exactly two tokens of equal decimals. The fee is 50 pips, 0.5 bps, half of Uniswap V3's lowest tier and an eighth of Curve 3pool. All of it goes to LPs; there's no protocol cut.
RangeConcentrated constant product with the band compiled in as virtual reserve offsets. The core step is one multiplication and one division, with no ticks, bitmaps or traversal loops, and it holds native ETH rather than WETH. Different pools cover different bands; the router quotes them all and uses whichever covers the current price.
OracleNo curve at all. Chainlink sets the price and swaps execute at it, plus a fee that scales with how stale the feed is: 1 bp just after an update, 50 bps at the one-hour heartbeat. Price impact is zero at any size. The staleness ramp also means the first swap after a price move pays the maximum, which is what makes sandwiching an oracle update unprofitable. Without a bonding curve there's no curve-based LVR, the largest source of LP loss on V3 ETH/USDC.

PrecisionPoolFactory generalizes the range design, taking the pair, band and fee as constructor arguments behind CREATE2 with an on-chain registry, while leaving the AMM step untouched. Around it sit PrecisionRoute, the zRouter executor; PrecisionZap for single-sided entry; PrecisionPoolLens and PrecisionLiquidityLens for swap and LP previews; and PrecisionPoolPolicy.

Ours are end-to-end through an EIP-7702 batch wallet, measured in Foundry fork tests against mainnet. Competitor figures come from their official snapshots; gas is pair-independent in generalized AMMs. The pools are also reachable through zRouter.snwap or a multisig executeBatch.

The suite is live and verified on mainnet as of 11 August 2026, but unseeded: poolCount() is 0, so no market exists yet and nothing holds user funds.
